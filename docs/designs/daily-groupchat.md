## Problem Statement

You want hands-on side projects that are fun to build and fun to show people. This one turns a week of your friends' Apple Messages group chat into a one-page satirical newspaper. Every Sunday morning a draft arrives on your phone. You reply `ship` and it posts into the group as an image.

## What Makes This Cool

- **It's about the people reading it.** Every headline is an inside joke ("LOCAL MAN STILL HASN'T RETURNED TUPPERWARE").
- **Tapbacks are real data.** Messages stores every ❤️ 😂 ‼️ reaction, so "Quote of the Week" is the message the group actually loved most, and "Funniest Person" is whoever got the most 😂. No other chat export gives you this.
- **It just shows up.** Nobody runs anything. The paper arrives on Sunday, and you're the editor who approves it from your phone.

## Constraints

- Runs **only on your Mac**. It reads `~/Library/Messages/chat.db`. Nothing is built or run in a cloud container.
- The process needs **Full Disk Access** to read chat.db. Sending messages needs **Automation permission** for Messages.
- The week's chat text is sent to the Claude API. The group should know this exists and agree to it (see the Assignment).
- The Mac must be on or wake up on Sunday. launchd runs a missed calendar job when the Mac wakes.

## Premises (agreed)

1. You share an **image posted in the group chat**, not a link.
2. **Apple Messages (iMessage)** is the source, read straight from chat.db. (Changed from WhatsApp during the session.)
3. **Facts come from code and jokes come from Claude.** Code computes the stats, the tapback counts and the issue number, and the template inserts them directly. Claude's prose never supplies numbers that get printed. Every quote Claude uses is a structured `{sender, text}` entry that is checked word for word against the chat, and any quote that fails the check is dropped. Numbers Claude mentions inside its jokes are not checked. That's covered by your review before posting.
4. **Roast, don't wound.** The prompt forbids health, relationships, money and anything said in confidence. Nothing posts until you approve it.
5. Lives in `side-projects/daily-groupchat/` and **reuses the Claude call and error handling from `research-summarizer/summarize.py`**.

## Recommended Approach: C, the Editor in Your Pocket

You chose it for the "it just shows up" magic and to learn macOS automation (launchd, AppleScript).

### Pipeline (one Python package, five steps)

1. **extract.py**: Copy `chat.db`, `chat.db-wal` and `chat.db-shm` to a temp dir and open the copy read-only. Never touch the live database.
   - Select the configured group chat by its `chat.guid` (pinned in `config.toml`).
   - Join `chat_message_join → message → handle` and pull the last 7 days.
   - **Dates** are nanoseconds since 2001-01-01: `unix = date / 1e9 + 978307200`.
   - **Text**: on recent macOS, `text` is often NULL and the content lives in the `attributedBody` blob (an NSAttributedString typedstream). Decode it with the `pytypedstream` package, or with the known `NSString` byte-offset hack as a fallback. Count how many rows decode to empty and log it.
   - **Tapbacks**: rows where `associated_message_type` is 2000–2006 are reactions to the message named in `associated_message_guid` (strip the `p:0/` or `bp:` prefix). 3000–3006 are removals; subtract them.
   - **Names**: map `handle.id` (phone or email) to a display name through `names.json`. Unknown handles show as "A Mysterious Stranger".
   - **Which rows count as messages.** Only rows where all of these hold become part of the transcript, the stats and the quote candidates: `associated_message_type = 0` (not a tapback), `item_type = 0` (not a group event such as a rename or someone joining), a non-empty decoded text, and not retracted. Tapback rows are used only for reaction counts. Rows that are only an attachment or sticker are left out.
   - **Unsent and edited messages.** Retracted (unsent) messages are excluded completely: they never reach Claude, the stats or the quotes. Edited messages use only their latest text, never the edit history. Check the exact column names (`date_retracted`, `date_edited`) during step 1(b), and add a fixture row for each case.
2. **stats.py** (no LLM): counts per person over content rows only: message count, share of total, messages sent between 2am and 5am, and 😂 received. Also the top emoji, the most-tapbacked text message, and the issue number (count of posted issues + 1).
3. **write.py**: One Claude call that returns structured JSON with these fields: `lead_headline`, `lead_story`, `quotes: [{id, sender, text}]`, `quote_of_week_id`, `op_ed {author, title, blurb}`, `vibe_forecast`, `corrections`.
   - **Quotes appear in the prose only as placeholders** like `{{q1}}`. The template fills them in with the checked text.
   - **Numbers come from code, not Claude.** Claude never writes the issue number or the stats box. The template fills those from stats.py.
   - **Inputs**: the transcript, using only display names from names.json (raw phone numbers and emails never go to the API). Plus the stats, the most recent *posted* issue's JSON (so corrections can call back to it), and any editor notes.
   - **The system prompt** holds the "roast, don't wound" rules.
   - **Long weeks** get trimmed to the most recent messages so they fit a fixed token budget.
   - **What's reused from `summarize.py`**: how the client is set up and how API errors are turned into readable messages. Structured output, the larger output budget and the token trimming are new code.
4. **verify.py**: Check each entry in `quotes` against that sender's messages from the **full week**, not just the trimmed part Claude saw. Text is compared after normalizing whitespace, case and curly versus straight quote marks, and a match must be a word-for-word substring.
   - A quote that fails is removed, along with its placeholder.
   - Any text inside quotation marks in the prose that isn't a placeholder counts as an unverifiable quote. The issue gets regenerated once, and if it fails again the run fails (see Failure handling).
   - If `quote_of_week` fails, fall back to the most-tapbacked text message. Like everything else, you see it in the draft before anything posts.
5. **render.py**: Fill the Jinja2 newspaper template, then screenshot it with Playwright at 1080 px wide and 2x pixel density to get `issues/<date>-v<N>.png`. Save `issues/<date>-v<N>.json` next to it.

### Delivery and approval loop (the C part)

Both jobs share `state.json`. It is always written to a temp file and then renamed, so a crash can never leave half a file:

```
{ issue, draft_version, status, window_start, cursor_rowid, rewrites }
status: awaiting_reply | rewriting | posting | posted | dry_posted
        | skipped | expired | failed | unknown_send
```

- **How the bot ignores its own texts.** Every message the bot sends starts with the prefix `🗞️ [bot]`, and the draft caption says `Draft vN`. `cursor_rowid` moves only past rows that job 2 has actually looked at. It never jumps ahead to the newest row. A self-chat row counts as a reply only if all of these are true:
  - its ROWID is greater than `cursor_rowid`
  - it has no attachment, and its text isn't empty or just the U+FFFC placeholder character (your replies are always plain text)
  - it doesn't start with the bot prefix
  - it isn't the same text as a reply already handled in the last 120 seconds. A message to yourself shows up twice in chat.db, once as sent and once as received, so the second copy counts as a duplicate.

  Bot attachments that show up late and second copies of the bot's own messages fail these rules, so they can never be mistaken for editor notes.
- **Reply matching.** Before matching, a reply is trimmed, lowercased, and stripped of trailing punctuation, spaces and emoji, so "Ship", "ship." and "Skip " all count. After that, it's `ship` if it equals `ship` or `post` and `skip` if it equals `skip`. Anything else is editor notes.
- **Each reply is handled exactly once.** Job 2 handles one reply per row, in order, and moves `cursor_rowid` forward right after each one.
- **A reply applies to the draft you could see when you sent it.** state.json keeps `delivered_at` for the newest draft. A `ship` sent before the newest draft arrived approves an older draft you haven't seen, so it doesn't post. The bot texts "that ship was for an older draft, reply ship again to post Draft vN". Notes sent during a rewrite wait in line and are applied in the next rewrite.
- **`launchd` job 1, Sunday 09:00** (`StartCalendarInterval`).
  - If last week's state was never finished, it gets marked `expired` first.
  - Then it runs the pipeline, texts Draft v1 to **your own** number or Apple ID via `osascript`, and sets `status=awaiting_reply`, `draft_version=1`, `rewrites=0` and `window_start=now`.
- **`launchd` job 2, every 2 minutes** (`StartInterval`). It does nothing unless the status is `awaiting_reply`, `rewriting` or `posting`. A file lock stops two ticks from overlapping.
  - **`ship`** is accepted only when the status is `awaiting_reply`, and it approves the most recently delivered draft, which is the only one you can have seen.
    - Before sending anything it saves `status=posting`.
    - Then it re-checks the target chat GUID against config, copies the PNG into the folder Messages can read, and posts.
    - On success the status becomes `posted`.
    - **When a crash leaves a post half-done, the bot asks you to check instead of retrying.** Job 2 also wakes up when the status is `posting`. If it finds `status=posting` left behind by an earlier tick, it **never retries**. It sets `unknown_send` and texts you "not sure issue #N posted, check the group". An exception thrown during the post step itself has the same result: `unknown_send` with that same text, never `failed`. Before job 1 next Sunday marks an unfinished state `expired`, it repeats this warning if the status was `posting` or `unknown_send`. So a crash can't cause a double post or a silent miss.
  - **`skip`** sets the status to `skipped`.
  - **Anything else counts as editor notes.** The status becomes `rewriting`, and write → verify → render runs again with the notes. Then Draft vN+1 is sent, `draft_version` and `rewrites` go up by one, `window_start` resets, and the status goes back to `awaiting_reply`.
  - **After 3 rewrites**, notes get the reply "rewrite limit reached, reply ship or skip".
  - **No reply within 6 hours of `window_start`** sets the status to `expired`, and the bot texts "issue #N was not posted".
- **Failure handling.** Any exception in either job does three things:
  - sets `status=failed`, so job 2 does nothing after that
  - texts you `🗞️ [bot] issue #N failed: <one-line reason>, log: <path>`
  - writes the full error to `logs/`, which is the `StandardErrorPath` in both plists

  This covers chat.db or Full Disk Access errors, Claude API errors, a second failed quote check, and Playwright errors. Pipeline code raises exceptions instead of calling `SystemExit`. If the failure text itself can't be sent, the log is the only record.
- **The API key under launchd.** launchd jobs don't see your shell's environment variables, so both plists run a `run.sh` wrapper instead. It reads the key with `security find-generic-password -s daily-groupchat -w` from the macOS Keychain and exports `ANTHROPIC_API_KEY`. `install.sh` stores the key in the Keychain once. The key never goes into a plist or the repo.
- **Dry-run vs live.** `live = true` in `config.toml` is the only thing that enables real posting. The default is `false`, and a `--dry-run` flag on the command line always forces dry-run, whatever the config says. In dry-run everything runs for real, including the texts to you. The only difference is that `ship` texts "DRY RUN: would have posted Draft vN to <chat name>" and sets `dry_posted` instead of posting.
- **Safety rails**: The group chat GUID is hard-coded in config and never inferred. Nothing gets sent anywhere except your self-chat and that one GUID.

## Open Questions

1. **Full Disk Access under launchd.** Background jobs don't inherit Terminal's Full Disk Access. You probably need to grant it to the specific `python3` binary the plist runs. Verify this in the first test run.
2. **Sending images with AppleScript.** Attaching a file to a Messages send has been flaky on recent macOS. Files may need to sit in a folder Messages can read, such as `~/Pictures`. This is the riskiest part of the plan, so test it before building anything else (Next Steps, step 1).
3. **Reading replies from the self-chat.** Confirm how your own replies appear in chat.db (`is_from_me`, duplicate rows). If it's too messy, fall back to approving by replying from a second Apple ID, or with a `groupchat ship` command on the Mac.
4. **Roast intensity.** Should `config.toml` have a "spice" setting from 1 to 3? That's your call on taste.

**Problem**
